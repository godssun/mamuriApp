# 일기 사진 중복 저장 — 실기기 이슈 수정

## 문제 요약
일기 수정 후 저장 시 사진이 중복 생성되는 문제. 시뮬레이터에서는 재현이 어렵고 실기기(배포 빌드)에서 주로 발생.

## 재현 경로
1. 사진 포함 일기 작성 → 저장
2. 수정 화면 재진입
3. 사진 위치 이동 또는 크기 변경
4. 저장
5. 상세 화면에서 사진이 2장 이상으로 중복되어 보임

## 근본 원인 분석

### 원인 1: 더블탭 Race Condition (실기기 전용)
- `saving` 상태가 React state로만 관리되어, 실기기에서 렌더 지연 시 더블탭으로 `handleSave`가 두 번 실행될 수 있음
- 동일 사진이 두 번 업로드되어 서버에 중복 레코드 생성
- 시뮬레이터에서는 렌더가 빨라 재현이 어려움

### 원인 2: 서버 URL 사진의 photoId 유실 가능성
- 편집 시 로드된 사진은 `photoId`(서버 ID)를 가짐
- 이론적으로 state 업데이트 과정에서 `photoId`가 유실되면, 해당 사진이 "새 사진"으로 분류되어 재업로드됨
- 실기기에서 메모리 압박이나 컴포넌트 재마운트 시 발생 가능

### 원인 3: 커스텀 스티커 매 저장 시 재업로드
- 커스텀 스티커(cs_ 접두사)가 사진으로 업로드됨
- 편집 모드에서 기존 커스텀 스티커의 URI가 서버 URL인데도 재업로드 여부를 체크하지 않음

### 원인 4: 삭제된 사진 서버 미반영
- 캔버스에서 사진을 삭제해도 서버에서는 유지됨
- 다음 편집 시 서버에서 삭제된 사진이 다시 로드되어 중복처럼 보임

## 수정 내용

### Fix A: savingRef 가드 추가
- `useRef(false)`로 즉시 재진입 방지
- state 업데이트 지연과 무관하게 동기적으로 차단

### Fix B: initialPhotoIds 추적 + 서버 삭제
- 편집 로드 시 기존 사진 ID 배열 저장
- 저장 시 캔버스에 남아있는 사진 ID와 비교
- 제거된 사진은 `diaryPhotoApi.delete()` 호출

### Fix C: 서버 URL 사진 재업로드 방지
- `newPhotos` 필터에 `!photoUri.startsWith('http')` 조건 추가
- photoId 유실 시에도 서버 URL 사진은 재업로드되지 않음

### Fix D: 커스텀 스티커 서버 URL 체크
- 커스텀 스티커 저장 시 URI가 `http`로 시작하면 업로드 건너뜀

## 수정 파일
- `mobile/src/api/client.ts` — `diaryPhotoApi.delete()` 메서드 추가
- `mobile/src/screens_v2/DiaryCanvasEditorV3.tsx` — 4개 수정 적용

## 실기기 vs 시뮬레이터 차이
| 항목 | 시뮬레이터 | 실기기 |
|------|-----------|--------|
| 렌더 속도 | 빠름 (더블탭 window 거의 없음) | 상대적 지연 가능 |
| 네트워크 | localhost 직접 연결 | 원격 서버 경유 |
| 메모리 압박 | 낮음 | 앱 전환 시 컴포넌트 재마운트 가능 |
| URI 형식 | file:// 안정적 | 임시 파일 경로 변동 가능 |

## 재발 방지
- savingRef 패턴은 다른 저장 버튼에도 적용 권장
- 사진 관련 API 호출은 항상 idempotent하게 설계
- 서버 URL 사진은 절대 재업로드하지 않는 원칙 유지

## 검증 시나리오
1. 사진 1장 일기 저장 → 수정 진입 → 위치 이동 → 저장 → 1장 유지 확인
2. 사진 1장 + 새 사진 1장 추가 → 저장 → 총 2장 확인 (중복 없음)
3. 사진 2장 중 1장 삭제 → 저장 → 1장만 남음 확인
4. 빠른 더블탭으로 저장 → 중복 없음 확인
5. 커스텀 스티커 포함 일기 수정 → 저장 → 스티커 중복 없음 확인
